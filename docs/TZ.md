# ТЗ: Claude Autopilot

Nov 20, 2026 · @MorganLee7253

## 1. Цель и границы

Claude Autopilot — локальное приложение для macOS. Пока разработчик работает за компьютером, оно в фоне ведёт его open source проекты через Claude Code: берёт GitHub Issues, выполняет их по git-flow разработчика, вливает в `develop` и предлагает новые доработки. Человек подтверждает только две вещи: идеи для новых задач и PR из `develop` в `main`.

Пользователь один: владелец репозиториев на `github.com/prog-time`. Приложение работает на его Mac и слушает только `127.0.0.1`.

| Делает Claude (через Autopilot) | Делает человек |
| --- | --- |
| Раз в N минут проверяет открытые issues во всех проектах | Одобряет или отклоняет идеи, при желании правит текст |
| Выполняет issue командой `/task_complete`: ветка `issues-N` от `develop`, реализация, PR в `develop` | Открывает и мержит PR `develop` → `main` |
| Ждёт CI. Если CI упал или есть конфликт, сам чинит, до N попыток | Запускает релиз (скилл `git-release`) кнопкой в панели |
| Squash-merge PR в `develop` после зелёного CI (делает приложение, не Claude) | Отвечает на вопросы Claude и разрешает нестандартные команды |
| Анализирует простаивающие проекты и предлагает исправления и новый функционал | Меняет число потоков и ставит работу на паузу |
| После одобрения идеи создаёт issue через `/task_create` |  |

Вне рамок первой версии: работа с чужими репозиториями, несколько пользователей, удалённый доступ к панели, Windows и Linux.

Рабочий прототип (Node.js без фреймворков) уже есть и проверен на заглушках. Это ТЗ описывает полноценную реализацию; прототип служит справочником по логике конвейера. Дизайн панели — на холсте [Claude Autopilot — дизайн панели](https://claude.ai/artifact/FEV9xvZGTNtJbE1VN7gRfN).

## 2. Стек

TypeScript на всём проекте: бэкенд на Node.js с Claude Agent SDK, фронтенд на React, общие типы и схемы в одном монорепозитории.

| Слой | Выбор | Почему |
| --- | --- | --- |
| Язык | TypeScript 5, `strict` | Один язык для бэкенда и фронта, общие типы событий и API |
| Рантайм | Node.js 22 LTS | Требование Agent SDK; стабильный `node:test`/`fetch` |
| Агент | `@anthropic-ai/claude-agent-sdk` (TypeScript) | Тот же движок, что Claude Code: `canUseTool`, `AskUserQuestion`, `resume`, загрузка `~/.claude` через `settingSources`. TS-версия SDK развивается первой |
| HTTP | Fastify 5 + `@fastify/static` | Быстрый, типизированный, схемы через zod (`fastify-type-provider-zod`) |
| Живые обновления | Server-Sent Events | Односторонний поток событий; проще WebSocket, автопереподключение в браузере |
| Хранилище | SQLite: `better-sqlite3` + Drizzle ORM + drizzle-kit (миграции) | Один файл, транзакции, синхронный и быстрый; WAL для параллельных чтений |
| Валидация | zod | Одни схемы для config.json, API и SSE-событий |
| Внешние команды | `execa` + `git`, `gh` CLI | `gh` берёт авторизацию из `gh auth login`, токены хранить не нужно |
| Логи | pino (+ pino-pretty в dev) | Структурные логи в `~/.claude-autopilot/logs` |
| Фронтенд | React 19 + Vite 6 + Tailwind CSS 4 | Быстрая сборка; токены дизайна из макета ложатся в `@theme` |
| Данные на фронте | TanStack Query + свой хук `useEventStream` | Кэш запросов, SSE точечно обновляет кэш |
| Шрифты | Inter, JetBrains Mono (`@fontsource`) | Как в макете; локально, без запросов к Google |
| Тесты | Vitest, Playwright | Юнит и интеграция на заглушках; e2e панели |
| Качество | ESLint 9 (flat), Prettier, `tsc --noEmit` | Проверяется в CI и pre-push |
| Пакеты | pnpm workspaces | Монорепозиторий из трёх пакетов |
| Автозапуск | launchd (LaunchAgent) | Старт при входе в систему, перезапуск при падении |

Почему не Python или PHP: Python-SDK тоже есть, но тогда фронтенд и бэкенд живут на разных языках и типы событий придётся дублировать. Для PHP официального Agent SDK нет. Версии пакетов — на момент написания ТЗ; при старте брать актуальные стабильные.

## 3. Архитектура

Один процесс Node.js держит API, конвейер и все сессии Claude; панель в браузере только показывает состояние и отправляет решения.

&#91;embedded content: архитектура · сервер, панель, GitHub, сессии Claude\]

Конвейер сам ходит в GitHub (опрос, CI, мерж в develop), а код пишут только сессии Claude в рабочих клонах, и каждое их действие проходит проверку AgentRunner.

Структура репозитория:

```
claude-autopilot/
├─ packages/
│  ├─ shared/            # zod-схемы: config, API, SSE-события, статусы
│  ├─ server/
│  │  ├─ src/
│  │  │  ├─ main.ts        # старт, lock-файл, graceful shutdown
│  │  │  ├─ config/        # загрузка и hot reload config.json
│  │  │  ├─ db/            # Drizzle-схема, миграции, репозитории данных
│  │  │  ├─ events/        # шина событий → SSE
│  │  │  ├─ api/           # Fastify-маршруты, защита Host/Origin
```

## 4. Жизненный цикл задания

Задание типа `issue` проходит путь от очереди до релиза. Человек вмешивается только в `waiting_human`, `blocked` и на релизе.

&#91;embedded content: статусы задания issue · 7 состояний\]

Основной путь идёт слева направо без участия человека; красный CI возвращает задание в очередь на автоисправление. `cancelled`, `skipped`, `closed` и `failed` не показаны.

### 4.1. Синхронизация issues

Раз в `pollIntervalMinutes` и по кнопке для каждого включённого проекта (параллельно, до `ioConcurrency`):

1. `gh issue list --state open` → отбросить issues с `skipLabels`, без `onlyLabels` (если заданы) и от недоверенных авторов (раздел 11).
2. Для нового issue проверить PR из ветки `issues-N`: смержен в `develop` → `in_develop`; открыт → `pr_open`; нет → `queued`.
3. Issue закрыт на GitHub: из `in_develop` → `released`, из остальных незавершённых → `closed`.
4. Обновить релиз (4.5) и решить, нужен ли поиск идей (4.3).

Монитор PR раз в `ciPollSeconds` смотрит каждое задание `pr_open`: `MERGED` → `in_develop`; `CLOSED` → `cancelled`; конфликт или красный CI → автоисправление (до `maxCiFixAttempts`, потом `blocked`); CI идёт или `mergeable = UNKNOWN` → ждать; пустой список проверок меньше 3 минут после push → ждать (CI ещё не стартовал); всё зелёное и `autoMergeToDevelop` → `gh pr merge --squash --delete-branch`.

### 4.2. Статусы

| Статус | Значение |
| --- | --- |
| `queued` | Ждёт свободный поток и слот проекта |
| `running` | Сессия Claude работает |
| `waiting_human` | Сессия ждёт ответа на вопрос или разрешение |
| `pr_open` | PR в `develop` открыт, идёт CI (`ci_state`: `pending`, `success`, `ci`, `conflict`) |
| `in_develop` | Влито в `develop`, issue открыт до релиза |
| `released` | Issue закрыт релизом |
| `blocked` | Claude остановился без PR или CI не чинится |
| `failed` | Исключение (нет `develop`, ошибка git/gh/SDK) |
| `cancelled`, `skipped`, `closed` | Остановлено человеком, пропущено, issue закрыт без релиза |
| `done` | Задания `propose`, `create`, `release`, `fix` завершены |

### 4.3. Идеи

- Задание `propose` ставится, когда у проекта нет заданий в `queued`/`running`/`waiting_human`, неразобранных идей меньше `maxPendingPerRepo` и с прошлого поиска прошло `intervalHours`. Или по кнопке «Идеи».
- Промпт: проанализировать проект на `develop` и предложить до `perRun` доработок (найденные ошибки с файлом и местом, функционал, надёжность, тесты, документация); не повторять открытые issues и прошлые идеи (списки передаются в промпте); ничего не менять; ответ закончить блоком \`\`\`json с массивом `{ title, type, size, rationale, description }`.
- Невалидный JSON → задание `done` с событием-предупреждением, идей 0.
- Одобрение (с правками) → задание `create` (`/task_create`) → из ответа берётся URL issue → идея `created` → сразу синхронизация проекта, новый issue встаёт в очередь. Нет URL → `failed`.

### 4.4. Решения для остановок

Когда задание останавливается и нужен человек (`failed`, `blocked`, CI не чинится), карточка в «Проблемах» несёт **предлагаемое решение**: что сделать, шаги и точные команды. Человек правит текст шагов и нажимает «Выполнить решение» — дальше действует Claude.

- **Источник решения**, по порядку: (1) рецепт для известной проблемы — без запуска Claude; (2) Claude остановился сам и закончил ответ блоком ```json `{"proposal": …}` (правило в `append` системного промпта); (3) иначе — сессия «только чтение» (`resume` той же сессии, если есть; до `remedies.maxTurns` ходов) разбирает причину и возвращает решение в том же формате.
- **Формат:** `{ summary, steps[], commands[], where: clone|local, needsHuman }`. `needsHuman: true` — решение только для человека (доступы, секреты, оплата, продуктовое решение): шаги показываются, кнопки «Выполнить» нет.
- **Рецепты:** нет `origin/develop`, а на GitHub есть ветки → `git push origin origin/<main>:refs/heads/develop` в клоне. Репозиторий на GitHub пустой, а `localPath` указывает на копию с тем же `origin` → в локальной папке: первый коммит (если коммитов нет), push основной ветки и `develop`. Нет подходящей локальной копии → решение `needsHuman`.
- **Выполнение:** у задания `issue` с живой сессией и `where = clone` — продолжение той же сессии (`resume`, приоритет 95), затем `/task_branch` и `/task_submit`. Иначе — задание `fix` (приоритет 95) в клоне или в `localPath`; после успеха исходное задание автоматически ставится заново.
- **Разрешения:** команды из одобренного решения записываются в `approved_commands` задания и проходят `canUseTool` без повторного вопроса, только при точном совпадении строки; после сессии список очищается. Команды в панели не редактируются, только шаги. Работа в `localPath` — единственное исключение из правила «Claude не работает в папках разработчика» и в карточке помечается отдельно.
- Задание `fix` само решений не предлагает (нет циклов); его падение — обычная карточка «Решение не выполнено».

### 4.5. Релиз develop → main

- После каждого мержа и синхронизации: `git log --no-merges origin/main..origin/develop` (merge-коммиты sync-develop не считаются).
- Есть коммиты → карточка «Релиз»: задачи в `in_develop`, коммиты, ссылка на открытый PR `develop → main` или на `compare/main...develop?expand=1`. Уведомление — один раз, при переходе от 0 коммитов.
- PR в `main` создаёт и мержит человек. Кнопка «git-release» ставит задание `release`; его команды `git tag`/`gh release` всё равно идут на подтверждение.

## 5. Claude Agent SDK, правила \~/.claude и разрешения

Autopilot не дублирует git-flow разработчика: он вызывает его команды из `~/.claude` и ограничивает Claude политикой разрешений.

### 5.1. Запуск сессии

Каждое задание = один вызов `query()` с параметрами:

- `cwd` — рабочий клон задания (раздел 6);
- `settingSources: ['user', 'project', 'local']` — подхватываются `~/.claude/CLAUDE.md`, команды `task_*`, скиллы, агенты и хуки из `~/.claude/settings.json`;
- `systemPrompt: { type: 'preset', preset: 'claude_code', append }` — `append` сообщает, что Claude работает автономно, ведёт план через TodoWrite, спрашивает через AskUserQuestion и не мержит PR;
- `permissionMode: 'acceptEdits'` для рабочих заданий, `'default'` для анализа;
- `canUseTool` — политика из 5.3;
- `abortController` — остановка из панели;
- `resume: sessionId` — продолжение сессии при автоисправлении CI и указаниях человека;
- `model`, `maxTurns` — из конфигурации.

### 5.2. Какие команды вызываются

| Задание | Промпт | Режим |
| --- | --- | --- |
| Выполнить issue | `/task_complete <url issue>` | рабочий |
| Починить CI | `/task_branch <url>`, логи через `gh pr checks` и `gh run view --log-failed`, исправление, `/task_submit`; запрещено отключать проверки и `--no-verify` | рабочий, `resume` |
| Разрешить конфликт | `/task_branch <url>` (вливает `develop`), разрешение, тесты, `/task_submit` | рабочий, `resume` |
| Указание человека | текст человека + `/task_branch`, `/task_submit` | рабочий, `resume` |
| Найти идеи | промпт анализа (раздел 4.3), ответ заканчивается блоком `json` | только чтение |
| Создать issue из идеи | `/task_create <заголовок>\n\n<описание>` | рабочий |
| Релиз | «Выпусти релиз скиллом git-release…», только по кнопке | рабочий |

Хук `pr-base-guard` разработчика остаётся жёстким стопом: Claude не может открыть PR не в `develop`. При старте приложение проверяет, что хук зарегистрирован в `~/.claude/settings.json`, и пишет предупреждение в панели, если нет.

### 5.3. Политика canUseTool

Решение принимается по порядку, первое совпадение побеждает:

1. Режим «только чтение»: разрешены Read, Glob, Grep, LS, TodoWrite, Task/Agent, WebSearch, WebFetch и Bash из списка читающих команд. Всё остальное запрещается сразу, без вопроса человеку.
2. `AskUserQuestion` → карточка «Вопрос»; ответ возвращается в `updatedInput.answers`. «Пусть решит сам» → `deny` с сообщением принять решение и отметить его в отчёте.
3. Инструмент из `autoAllowTools` → разрешён. Bash-команда, точно совпадающая с одной из `approved_commands` задания (одобренное решение, раздел 4.4), → разрешена.
4. Bash: команда делится по `&&`, `||`, `;`, `|` и переводам строки; префикс `VAR=value` отбрасывается. Разрешена, если каждая часть начинается с префикса из `autoAllowBashPrefixes`, нет подстановок `$(…)` и обратных кавычек и нет подстрок из `alwaysAskBashPatterns`.
5. Всё остальное → карточка «Разрешение» с предпросмотром (команда, diff правки, JSON входа), уведомление macOS, задание ждёт. Комментарий к запрету передаётся Claude.

По умолчанию всегда спрашиваются: `--force`, `push -f`, `--no-verify`, `reset --hard`, `rm -rf`, `sudo`, `gh pr merge`, `gh release`, `git tag`, `git push origin main`, `git push origin develop`, `curl`, `wget`, `docker`, `brew`.

### 5.4. Разбор потока сообщений

- `system/init` → сохранить `session_id`.
- `assistant`: текст → событие `text`; `tool_use` → событие `tool` с кратким описанием (команда, путь файла, скилл, субагент). Сообщения с `parent_tool_use_id` помечаются как субагентные (`↳`).
- `TodoWrite` верхнего уровня → обновить план задания.
- `user` с `tool_result.is_error` → событие `tool_error` (первые 1200 символов).
- `result` → стоимость, число ходов, итоговый текст, признак успеха.

Адаптер SDK вынесен за интерфейс `AgentRunner`, чтобы в тестах подменять его заглушкой.

## 6. Многопоточность и рабочие клоны

Несколько проектов и несколько задач одного проекта выполняются одновременно. Каждое задание получает свою сессию Claude (отдельный процесс от SDK) и свою папку-клон.

### 6.1. Рабочие клоны (слоты)

- Claude никогда не работает в папках разработчика (`~/code/…`). `/task_branch` переключает ветки и требует чистого дерева, поэтому у приложения свои клоны: `~/.claude-autopilot/repos/<owner>__<repo>` (слот 0) и `<owner>__<repo>@1`, `@2`… для параллельных задач.
- Один слот — одно задание в момент времени. git worktree не подходит: `git switch develop` падает, если `develop` уже выбрана в другом worktree.
- Подготовка слота перед каждым заданием:
  1. Нет клона → `git clone` по URL из `gh repo view`.
  2. Дописать в `.git/info/exclude`: `tasks/`, `github-tasks.json`, `.claude/settings.local.json`, чтобы файлы команд `task_*` не делали дерево «грязным».
  3. Скопировать неотслеживаемые файлы `.claude/` из локальной папки проекта.
  4. `git fetch origin --prune`; нет `origin/develop` → ошибка проекта в панели, задания не стартуют.
  5. Есть незакоммиченные изменения → `git stash push -u` (не удалять), запись в ленту.
  6. `git switch develop` и `git merge --ff-only origin/develop`.

### 6.2. Планировщик

| Лимит | По умолчанию | Диапазон | Что ограничивает |
| --- | --- | --- | --- |
| `concurrency` | 4 | 1–32 | Всего сессий Claude одновременно |
| `perRepoConcurrency` | 1 | 1–8 | Заданий одного проекта одновременно (= число слотов) |
| `ioConcurrency` | 6 | 1–16 | Параллельных запросов к GitHub при опросе и проверке CI |

- `pump()` вызывается по событиям (задание завершено, появилось новое, изменён лимит) и раз в 5 секунд.
- Очередь сортируется: приоритет (по убыванию) → номер issue → время создания. Приоритеты: автоисправление 100, указание человека 90, релиз 80, «взять следующим» 70, создание issue из идеи 50, issue 0, поиск идей −10.
- Для задания берётся свободный слот с наименьшим номером. Нет свободного → задание пропускается, планировщик идёт к следующему (потоки не простаивают).
- Продолжение сессии (`resume`) идёт только в том же слоте: сессии SDK привязаны к `cwd`.
- Лимиты меняются на лету из панели и сохраняются в БД поверх `config.json`. Снижение лимита не останавливает работающие задания, только не даёт стартовать новым.
- Задание, которое ждёт человека, держит свой поток и слот.
- Пока есть хотя бы одно запущенное задание, держится `caffeinate -i -w <pid>`. Весь процесс запускается с `nice -n 10`, чтобы IDE и браузер разработчика не тормозили.

### 6.3. Перезапуск приложения

Задания в статусах `running` и `waiting_human` при старте возвращаются в `queued`, их открытые вопросы и разрешения закрываются. Это безопасно: `/task_complete` идемпотентен и продолжает существующую ветку `issues-N`.

## 7. Модель данных

Все данные лежат в одном файле SQLite `~/.claude-autopilot/autopilot.db` (режим WAL). Схема описана в Drizzle, миграции применяются при старте. Даты — ISO-строки UTC, id — ULID.

| Таблица | Ключевые поля | Назначение |
| --- | --- | --- |
| `repos` | `slug` (PK, `owner/name`), `local_path`, `enabled`, `error`, `last_sync_at`, `last_proposal_at` | Найденные проекты и их состояние |
| `jobs` | `id`, `kind` (`issue`\|`propose`\|`create`\|`release`\|`fix`), `repo`, `status`, `title`, `issue_number`, `issue_url`, `pr_url`, `pr_number`, `pr_since`, `ci_state`, `slot`, `session_id`, `follow_up`, `fix_attempts`, `priority`, `todos` (JSON), `last_activity`, `cost_usd`, `turns`, `result_text`, `error`, `idea_id`, `fix_for`, `proposal` (JSON), `approved_commands` (JSON), `created_at`, `updated_at`, `started_at` | Задания Claude. Уникальный индекс `(repo, issue_number)` для `kind = issue` |
| `job_events` | `id`, `job_id`, `ts`, `kind` (`system`\|`text`\|`tool`\|`tool_error`\|`human`\|`result`\|`error`), `tool`, `text`, `sub` (субагент), `meta` (JSON) | Лента выполнения. Индекс `(job_id, id)` |

| `releases` | `repo` (PK), `ahead`, `commits` (JSON, до 30), `pr_url`, `updated_at` | Что лежит в `develop` и не в `main` |

## 8. API

REST для чтения и команд, SSE для живых обновлений. Все тела запросов и ответов описаны zod-схемами в `packages/shared`. Ошибки — `{ error: { code, message } }` с кодом 400/404/409.

| Метод и путь | Тело | Что делает |
| --- | --- | --- |
| `GET /api/state` | — | Снимок: задания (без событий), открытые решения, идеи `pending`, проекты, релизы, лимиты, пауза, время последнего опроса |
| `GET /api/jobs?status=&repo=&kind=&cursor=` | — | Список заданий с фильтрами и пагинацией |
| `GET /api/jobs/:id/events?after=` | — | Лента задания (последние 800 или после `after`) |
| `POST /api/jobs/:id/cancel` | — | Остановить или пропустить |
| `POST /api/jobs/:id/retry` | — | Заново в очередь, счётчик автоисправлений = 0 |
| `POST /api/jobs/:id/prioritize` | — | Приоритет 70 |
| `POST /api/jobs/:id/followup` | `{ message }` | Указание Claude, продолжение сессии |
| `POST /api/actions/:id/resolve` | `{ decision: allow\|deny\|dismiss, message?, answers? }` | Ответ на разрешение или вопрос; 409, если уже закрыто |
| `POST /api/actions/:id/apply` | `{ summary?, steps? }` | Выполнить предложенное решение (раздел 4.4); 409, если карточка закрыта или решения нет |
| `POST /api/ideas/:id/approve` | `{ title?, description? }` | Одобрить с правками → задание `create` |
| `POST /api/ideas/:id/reject` | — | Отклонить |
| `POST /api/repos/:owner/:name/propose` | — | Найти идеи сейчас |
| `POST /api/repos/:owner/:name/release` | — | Задание `release` (git-release) |
| `PATCH /api/repos/:owner/:name` | `{ enabled }` | Включить или выключить проект |
| `POST /api/sync` | — | Опросить GitHub сейчас |
| `PATCH /api/settings` | `{ concurrency?, perRepoConcurrency?, paused? }` | Лимиты и пауза |
| `GET /api/stream` | — | SSE-поток |
| `GET /api/health` | — | `{ ok, version, sdkVersion, ghAuth, hooksOk }` |

SSE-события (`event:` + JSON в `data:`): `job.updated`, `job.event`, `action.created`, `action.resolved`, `idea.updated`, `repo.updated`, `release.updated`, `settings.updated`, `sync.started`, `sync.finished`. Каждое несёт полный объект, чтобы клиент обновлял кэш без дополнительных запросов. Пинг раз в 25 секунд; после переподключения клиент запрашивает `/api/state` заново.

### 9.2. Экран «Панель» (≥ 1024 px)

1. **Шапка:** логотип, статус «Работает / На паузе», счётчики (потоки X из Y, очередь, PR на CI, время опроса), степперы «Потоки» и «на проект», кнопки «Проверить GitHub» и «Пауза».
2. **Полоса потоков:** карточка на каждое запущенное задание (проект, номер потока, статус, заголовок, последнее действие, прогресс плана) и пунктирные карточки свободных потоков. Ждущее человека — акцентная рамка. Клик открывает задание.
3. **Левая колонка (300 px):** вкладки «В работе / В develop / Все» со счётчиками, список заданий, блок «Проекты» (индикатор состояния, число активных заданий, кнопка «Идеи», текст ошибки).
4. **Центр — задание:** строка репозиторий · ветка · ссылки на issue и PR; заголовок; статус, план X/Y, время, стоимость, состояние CI; кнопки по статусу. Две колонки: «План Claude» (чек-лист из TodoWrite с прогрессом) и «Ход выполнения» (лента: время, чип инструмента, текст; субагенты с `↳`, ошибки красным, автопрокрутка, если пользователь внизу). Поле «Указание для Claude» — для статусов `pr_open`, `blocked`, `failed`, `in_develop` при наличии сессии.
5. **Правая колонка (390 px) «Ваши решения»** с общим счётчиком. Секции по порядку срочности: «Ждёт ответа» (вопросы — радио/чекбоксы + свой ответ; разрешения — предпросмотр и комментарий), «Релизы» (задачи в develop, список коммитов, «Открыть / Создать PR», «git-release» с подтверждением), «Идеи» (тип, размер, обоснование, редактируемое описание), «Проблемы» (blocked, CI не чинится, падения).

### 9.3. Телефон (< 768 px)

Нижняя навигация из четырёх разделов: Решения (по умолчанию), Задания, Идеи, Потоки. Кнопки не ниже 46 px, варианты ответа на всю ширину. Та же сборка, разная вёрстка по breakpoint. Доступ с телефона в первой версии — только при явно настроенном туннеле (раздел 11).

### 9.4. Состояния и поведение

- Пустые состояния: нет проектов (подсказка про `scan` в конфиге), нет заданий, нет решений («Решений не требуется — Claude работает сам»).
- Ошибки запуска: `gh` не авторизован, хуки не найдены, SDK не найден — баннер над панелью с инструкцией.
- Соединение SSE потеряно — плашка «Нет связи с сервером», автопереподключение.
- Новые решения не перерисовывают карточки, в которых пользователь печатает (ключи React по id).
- Счётчик решений дублируется в `document.title`: `(3) Autopilot`.
- Горячие клавиши внутри панели: `j`/`k` — следующее/предыдущее задание, `g s` — опрос GitHub. Не срабатывают в полях ввода.
- Доступность: настоящие `<button>` и `<label>`, `aria-label` на кнопках-иконках, контраст текста не ниже 4.5:1, статусы различаются не только цветом, но и текстом.

## 11. Нефункциональные требования и безопасность

### Безопасность

- Сервер слушает только `127.0.0.1`. Для доступа с телефона — только через туннель, настроенный пользователем (Tailscale), и с включённым токеном доступа (`auth.token` в конфиге, заголовок `Authorization: Bearer`).
- Защита от CSRF и DNS rebinding: проверка заголовка `Host` (`localhost`/`127.0.0.1`) и `Origin` на всех `POST`/`PATCH`, `Content-Type: application/json` обязателен.
- Никаких токенов GitHub и ключей Anthropic в БД, логах и конфиге: авторизация из `gh auth` и Claude Code. В ленте маскируются строки, похожие на секреты (`ghp_`, `sk-ant-`, `AKIA`, `-----BEGIN`).
- Внешние команды только через `execa` с массивом аргументов, без оболочки.
- В `main` пишет только человек: приложение никогда не мержит и не создаёт PR в `main`; хук `pr-base-guard` — вторая линия защиты.
- Автомерж в `develop` только для PR, которые открыл сам Autopilot (ветка `issues-N`, задание в БД), и только если автор PR = текущий пользователь `gh`. Чужие PR не трогается.
- Текст issues, комментариев и логов CI — данные от третьих лиц (open source: issue может написать кто угодно). По умолчанию брать в работу только issues, созданные владельцем или имеющие метку, поставленную владельцем (`issues.trustedAuthors`, по умолчанию — владелец репозитория). Чужие issues попадают в раздел «Идеи» на подтверждение.

### Надёжность

- Падение одного задания или проекта не влияет на остальные. Необработанные ошибки логируются, процесс не падает.
- Ошибки `gh` (rate limit, сеть) — повтор с экспоненциальной задержкой (3 попытки, до 30 с), затем ошибка проекта в панели.
- При падении или перезапуске ни одно задание не теряется (раздел 6.3). Graceful shutdown по SIGTERM: перестать брать задания, прервать сессии, вернуть их в очередь, закрыть БД.
- Два экземпляра не запускаются: lock-файл с PID.

### Производительность

- До 50 проектов и до 32 одновременных сессий без деградации панели.
- Открытие панели < 1 с, событие доходит до браузера < 300 мс.
- Запись событий в SQLite пачками (транзакция раз в 100 мс), чтобы 32 сессии не блокировали друг друга.
- Виртуализация ленты при больше чем 500 событиях (`@tanstack/react-virtual`).

### Наблюдаемость

- pino-логи в `~/.claude-autopilot/logs/app.log` с ротацией (10 МБ × 5).
- Статистика в панели: расход за день и неделю, заданий выполнено, доля заданий без вмешательства человека.

## 12. Тестирование

Весь конвейер проверяется без настоящего Claude и GitHub: на заглушке `AgentRunner`, фейковом `gh` и настоящем git с локальными bare-репозиториями. Так прототип уже проверен.

| Уровень | Инструмент | Что покрывает |
| --- | --- | --- |
| Юнит | Vitest | Политика Bash (табличные тесты: цепочки, подстановки, `VAR=x`, опасные шаблоны), сводка CI из `statusCheckRollup`, разбор идей из JSON-блока, фильтр issues, выбор слота и порядок очереди, схема конфига, маскировка секретов |
| Интеграция | Vitest + фейковый `gh` (скрипт с состоянием в JSON) + bare-репозитории во временной папке | Полный цикл issue → PR → CI упал → автоисправление → мерж → релиз; идея → `/task_create` → новый issue в очереди; вопрос и разрешение с ответом через API; перезапуск посреди задания; параллельные задания в 3 проектах и 2 слотах |
| API | Vitest + `fastify.inject` | Коды ответов, схемы, защита Host/Origin, 409 на повторное решение |
| UI | Vitest + Testing Library | Карточки решений не теряют введённый текст при SSE-обновлениях; степперы лимитов |
| E2E | Playwright | Сервер на заглушках: ответ на вопрос, одобрение идеи, смена лимита, вёрстка на 390 px и 1440 px, светлая и тёмная темы |
| Дымовой на реальном Claude | ручной скрипт `pnpm smoke` | Один тестовый репозиторий, один issue «добавить файл»; не в CI |

Покрытие `packages/server/src/{pipeline,policy,github,repos}` — не ниже 80% строк. CI: GitHub Actions на `macos-latest` (lint, typecheck, тесты, сборка) + workflow `git-process` из шаблона разработчика.

## 13. Этапы и задачи

Пять этапов, 24 задачи. Каждая задача = один issue: скопируйте строку в `/task_create` и сошлитесь на раздел ТЗ. Задачи внутри этапа идут по порядку зависимостей. После этапа 2 Autopilot можно запускать на самом себе.

### Этап 1. Каркас

- [ ] Монорепозиторий pnpm: `packages/shared`, `packages/server`, `packages/web`; TS strict, ESLint, Prettier, Vitest, ветки `main`/`develop`, CI (разделы 2, 3, 12)
- [ ] Конфиг: zod-схема, шаблон при первом запуске, переменные `AUTOPILOT_*`, hot reload (раздел 10)
- [ ] БД: Drizzle-схема, миграции, репозитории данных, пакетная запись событий, очистка старых (раздел 7)
- [ ] Шина событий + Fastify: `/api/state`, `/api/stream` (SSE), `/api/health`, защита Host/Origin, lock-файл, graceful shutdown (разделы 8, 11)

### Этап 2. Ядро конвейера

- [ ] Обёртки `git` и `gh` через execa: issues, PR, CI, мерж, релиз-PR; повторы и фейковый `gh` для тестов (разделы 4, 12)
- [ ] Проекты: автопоиск по `scan`, слоты-клоны, подготовка клона (exclude, `.claude/`, stash, `develop`) (раздел 6.1)
- [ ] `AgentRunner`: адаптер Agent SDK, разбор потока в события, план из TodoWrite, стоимость; заглушка для тестов (разделы 5.1, 5.4)
- [ ] Политика `canUseTool` и ожидание решения человека (вопросы, разрешения, режим «только чтение») + `POST /api/actions/:id/resolve` (раздел 5.3)
- [ ] Планировщик: очередь, приоритеты, лимиты, выбор слота, caffeinate, восстановление после перезапуска, `PATCH /api/settings` (раздел 6.2, 6.3)
- [ ] Синхронизация issues: фильтры меток и авторов, определение стадии по существующим PR, закрытые issues (раздел 4)
- [ ] Задание `issue`: `/task_complete`, поиск PR после сессии, статус `blocked` с карточкой (раздел 4)

## 14. Критерии приёмки

Версия 1.0 принята, когда на Mac разработчика выполнено всё ниже.

1. `autopilot install` ставит LaunchAgent; после перезагрузки панель открывается на `http://localhost:4777`, `autopilot doctor` без ошибок.
2. Issue от владельца в одном из проектов в течение одного интервала опроса попадает в очередь и выполняется через `/task_complete`. Появляется PR из `issues-N` в `develop`, коммиты соответствуют правилам `git-commit`.
3. Красный CI исправляется автоматически не более чем за `maxCiFixAttempts` попыток; иначе — карточка «CI не проходит». Зелёный CI → squash-merge в `develop`, issue остаётся открытым.
4. Три проекта работают одновременно при `concurrency = 4`; при `perRepoConcurrency = 2` две задачи одного проекта идут в двух клонах. Изменение лимитов в панели применяется без перезапуска.
5. Вопрос Claude и запрос на опасную команду появляются в «Ваших решениях» и уведомлении macOS; ответ из панели продолжает ту же сессию.
6. Ни одна сессия не сделала push в `main` или `develop`, force push, `--no-verify`, мерж PR без подтверждения человека.
7. Карточка «Релиз» показывает задачи в `develop`; кнопка git-release выпускает релиз и закрывает issues.
8. Идеи появляются раз в `intervalHours` для простаивающих проектов; одобренная идея за один цикл становится issue и уходит в работу.
9. Перезапуск приложения посреди задания не теряет задание; рабочие папки разработчика (`~/code/…`) не изменены.
10. Все тесты из раздела 12 зелёные в CI, панель проходит Playwright на 390 и 1440 px в обеих темах.
